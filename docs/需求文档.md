### 1.5 已找到的API接口

经过浏览器开发者工具Network面板抓取，页面实际使用的数据接口如下                                                                                                                                                                                                                                                                                                                      ：

#### 1.5.1 统计数据折线图API

**请求URL：**

```
GET https://bigdata.tuwan.com/sisters/getlineData?group={group}&game_id={game_id}&date_type={date_type}&ad_id={ad_id}&ad={ad}&data_start={data_start}&data_end={data_end}
```

**参数说明：**

| 参数           | 说明     | 可选值                 |
| ------------ | ------ | ------------------- |
| `group`      | 大厅过滤   | `all`=全部, 或具体大厅名称   |
| `game_id`    | 游戏过滤   | `all`=全部, 或具体游戏ID   |
| `date_type`  | 统计周期   | `1`=日, `2`=周, `3`=月 |
| `ad_id`      | 广告位ID  | `0`                 |
| `ad`         | 广告标签   | `总览`(URL编码)         |
| `data_start` | 数据起始索引 | `0`=默认              |
| `data_end`   | 数据结束索引 | `0`=默认              |

**返回格式：** JSON

```json
{
  "date": ["2026-04-27", "2026-04-28", ..., "2026-07-25"],
  "data": [0, 0, 0, ..., 90],
  "title": "新成团数",
  "title2": "预测数据",
  "actionInfo": {
    "title": "新成团数",
    "unit": "个",
    "col": "new_team_count",
    "type": 1,
    "percent": 0,
    "data": 0
  }
}
```

返回包含约90天的每日/周/月数据。通过切换`date_type`参数获取不同粒度的数据：

- `date_type=1` → **日**粒度（默认，约90天）
- `date_type=2` → **周**粒度（约13周）
- `date_type=3` → **月**粒度（约3个月）

**用法示例：**

```bash
# 获取日数据（所有大厅）
curl "https://bigdata.tuwan.com/sisters/getlineData?group=all&game_id=all&date_type=1&ad_id=0&ad=%E6%80%BB%E8%A7%88&data_start=0&data_end=0"

# 获取周数据（所有大厅）
curl "https://bigdata.tuwan.com/sisters/getlineData?group=all&game_id=all&date_type=2&ad_id=0&ad=%E6%80%BB%E8%A7%88&data_start=0&data_end=0"
```

#### 1.5.2 页面资源加载

统计数据页面（/sisters/tj）和基础数据页面（/sisters/detail/）的数据均通过**服务端渲染HTML**返回，前端使用：

- **DataTables**：表格数据展示与分页
- **ECharts**：折线图/柱状图展示（从getlineData接口获取数据）
- **Layer**：弹窗组件

**已确认：** 页面加载过程中没有发现独立的JSON数据API接口（XHR/JS请求过滤后仅发现`getlineData`图表数据接口），所有表格数据均包含在服务端渲染的HTML中直接返回。

## 二、核心指标体系

### 2.1 存量/增量指标

| 指标      | 定义            | 计算公式     | 粒度 |
| ------- | ------------- | -------- | -- |
| 新成团数    | 本周新成立的姐妹团数量   | 每日新成团数汇总 | 周  |
| 进行中姐妹团数 | 本周末仍在运行的姐妹团总数 | 周末取值     | 周  |
| 累计姐妹团数  | 截至本周的总团数      | 历史新成团累计  | 周  |

### 2.2 留存率指标（Retention）

| 指标     | 定义            | 计算公式                      | 粒度 |
| ------ | ------------- | ------------------------- | -- |
| 周留存率   | 本周结束时仍在进行的比例  | 周末进行中团数 ÷ 周初进行中团数 × 100%  | 周  |
| 新团7日留存 | 新成团7天后仍在进行的比例 | 7日后仍存活的新团 ÷ 当周新成团数 × 100% | 周  |
| 平均留存天数 | 所有姐妹团的平均存活天数  | 已成团天数平均值（基础数据）            | 周  |

### 2.3 解散率指标（Dissolution）

| 指标     | 定义         | 计算公式                       | 粒度 |
| ------ | ---------- | -------------------------- | -- |
| 周解散率   | 本周解散团数占比   | 本周解散数 ÷ ((周初+周末)/2) × 100% | 周  |
| 主动解散率  | 主动解散占总解散比例 | 主动解散数 ÷ 总解散数 × 100%        | 周  |
| 系统解散率  | 系统解散占总解散比例 | 系统解散数 ÷ 总解散数 × 100%        | 周  |
| 解散原因分布 | 按原因分类统计    | 手动解散 / 30天到期 / 违规解散 各占比    | 周  |

### 2.4 流水指标（Revenue）

| 指标      | 定义          | 计算公式             | 粒度 |
| ------- | ----------- | ---------------- | -- |
| 周礼物总流水  | 本周发放的礼物奖励总额 | 每日发放奖励金额汇总       | 周  |
| 单团平均流水  | 平均每个团的流水产出  | 总流水 ÷ 进行中团数      | 周  |
| 妹妹人均流水  | 妹妹端的平均累计流水  | 妹妹累计流水总和 ÷ 姐妹团总数 | 周  |
| 流水成就覆盖率 | 有流水成就的团占比   | 流水成就达成数 ÷ 总团数    | 周  |

### 2.5 活跃度指标（Activity）

| 指标       | 定义         | 计算公式                | 粒度 |
| -------- | ---------- | ------------------- | -- |
| 开车任务完成量  | 本周开车任务总次数  | 每日开车任务汇总            | 周  |
| 陪档任务完成量  | 本周陪档任务总次数  | 每日陪档任务汇总            | 周  |
| 收送礼任务完成量 | 本周收送礼任务总次数 | 每日收送礼任务汇总           | 周  |
| 综合活跃度指数  | 每团平均任务完成数  | (开车+陪档+收送礼) ÷ 进行中团数 | 周  |

### 2.6 成就/等级指标

| 指标       | 定义          | 计算公式                    | 粒度 |
| -------- | ----------- | ----------------------- | -- |
| 等级成就达成率  | 达成等级成就的团占比  | 等级成就达成数 ÷ 总团数           | 周  |
| 流水成就达成率  | 达成流水成就的团占比  | 流水成就达成数 ÷ 总团数           | 周  |
| 银箱子成就达成率 | 达成银箱子成就的团占比 | 银箱子成就达成数 ÷ 有效团数         | 周  |
| 妹妹等级分布   | 各等级妹妹数量占比   | 统计各等级（无/铜牌/银牌/金牌/王牌/大神） | 周  |
| 等级跃迁率    | 妹妹等级有提升的比例  | (最高等级≠当前等级) 的妹妹占比       | 周  |

### 3.2 对比维度

## 六、预警机制设计思路

### 6.1 预警思路总览

预警的核心目的是**主动发现异常变化，辅助运营及时干预**。建议从以下四个维度设计预警：

### 6.2 异常波动预警（数据突变检测）

| 预警项      | 触发条件            | 严重程度 | 建议应对            |
| -------- | --------------- | ---- | --------------- |
| 解散率突增    | 周解散率环比上升 > 20%  | 🔴 高 | 排查是否大厅规则变化/系统故障 |
| 解散率连续上升  | 连续2周解散率持续上升     | 🟡 中 | 关注整体趋势，检查政策副作用  |
| 新成团数骤降   | 周新成团数环比下降 > 30% | 🔴 高 | 检查招募渠道/新团引导流程   |
| 新成团数连续下降 | 连续2周新成团数下降      | 🟡 中 | 分析各大厅招募情况       |
| 流水大幅下降   | 周总流水环比下降 > 25%  | 🔴 高 | 检查流水产出大户的异常     |
| 流水连续下降   | 连续2周流水下降        | 🟡 中 | 关注流水分布变化        |
| 活跃度骤降    | 综合活跃度环比下降 > 30% | 🟡 中 | 检查任务系统是否正常      |

### 6.3 存量预警（指标触及阈值）

| 预警项        | 触发条件             | 严重程度 | 说明             |
| ---------- | ---------------- | ---- | -------------- |
| 进行中团数跌破临界值 | 进行中团数 < X（如<300） | 🔴 高 | 整体规模萎缩         |
| 某个大厅团数异常减少 | 单大厅团数周环比降 > 30%  | 🟡 中 | 该大厅可能出现问题      |
| 系统解散占比过高   | 系统解散占比 > 80%     | 🟡 中 | 多数是到期解散还是违规解散？ |

### 6.4 结构变化预警（健康度指标）

| 预警项       | 触发条件               | 严重程度 | 说明        |
| --------- | ------------------ | ---- | --------- |
| 头部集中度过高   | TOP5大厅占总团数 > 80%   | 🟡 中 | 过度依赖少数大厅  |
| 流水集中度过高   | TOP20%的团贡献 > 80%流水 | 🟡 中 | 长尾团流水产出不足 |
| 低等级妹妹占比过高 | 无/铜牌占比 > 70%       | 🟢 低 | 妹妹成长速度慢   |
| 短期团占比过高   | 存活<7天的团占比 > 40%    | 🟡 中 | 大量团的留存质量差 |

### 6.5 UID级别预警（个人维度）

| 预警项     | 触发条件          | 严重程度 | 说明       |
| ------- | ------------- | ---- | -------- |
| 连续无排档   | 连续2周排档天数 = 0  | 🟡 中 | 队长可能已流失  |
| 流水锐减    | 当周流水环比降 > 50% | 🟡 中 | 个人产出大幅下降 |
| 违规记录    | 本周出现违规处罚      | 🔴 高 | 关注违规类型   |
| 临近保护期结束 | 保护期将在1周内结束    | 🟢 低 | 提前关注是否续约 |

### 6.6 预警展现形式

```
┌──────────────────────────────────────────────────────────┐
```

## 七、数据变化突出展示方案

### 7.1 变化标识体系

| 变化幅度         | 标识 | 颜色    | 适用场景                          |
| ------------ | -- | ----- | ----------------------------- |

| 小幅上升（0\~10%） | ↑  | 🟢 浅绿 | —                             |
| 基本持平（±1%内）   | →  | ⚪ 灰色  | —                             |
| 小幅下降（0\~10%） | ↓  | 🟡 黄色 | —                             |
| 大幅下降（>10%）   | ↓↓ | 🔴 红色 | 利好指标用红色；利空指标用绿色               |

### 7.2 突出变化的方式

| 方式      | 说明                   | 示例                    |
| ------- | -------------------- | --------------------- |

| 趋势线标注   | 图表末端自动标注最近变化趋势       | 箭头 + 变化率文本            |
| 异常点高亮   | 超出正常范围的点在图表中高亮       | 红色圆点标记                |
| 颜色编码    | 利好方向用绿色，利空方向用红色      | 色盲友好的同时辅助判断           |
| 变化排行榜   | 各大厅按指标变化幅度排序         | 「变化最大TOP3 / 变化最小TOP3」 |

### 10.3 Git版本管理

#### 10.3.1 Git Bash部署管理

使用 **Git Bash** 进行完整的版本管理，所有代码入库，方便版本更新与回退。

**初始化流程：**

```bash
# 进入项目目录
cd /d/姐妹团看板系统

# 初始化Git仓库
git init

# 创建.gitignore
echo "*.db
*.sqlite
*.csv
*.xlsx
__pycache__/
.venv/
venv/
node_modules/
.env
.DS_Store
Thumbs.db

# 首次提交
git add .
git commit -m "feat: 初始化姐妹团数据统计报表系统"

# 关联远程仓库（如果有）
git remote add origin <远程仓库地址>
git push -u origin main
```

#### 10.3.2 分支策略

| 分支          | 用途     | 说明                             |
| ----------- | ------ | ------------------------------ |
| `main`      | 生产分支   | 已部署到Docker的稳定生产代码              |
| `develop`   | 开发分支   | 日常开发集成                         |
| `feature/*` | 功能分支   | 新功能开发（如 `feature/uid-query`）   |
| `hotfix/*`  | 紧急修复分支 | 生产问题紧急修复（如 `hotfix/alert-bug`） |

#### 10.3.3 版本更新流程

```bash
# 日常更新（开发环境）
git add .
git commit -m "feat: 新增XXX功能"
git push origin develop

# 合并到生产
git checkout main
git merge develop
git tag v1.0.1
git push origin main --tags

# 部署最新版本
docker-compose down
docker-compose up -d --build
```

#### 10.3.4 版本回退流程

| 场景       | 操作        | 命令                               |
| -------- | --------- | -------------------------------- |
| 回退到上一版本  | 保留修改但撤销提交 | `git reset --soft HEAD~1`        |
| 回退到指定版本  | 保留修改      | `git reset --soft <commit-hash>` |
| 强制回退     | 丢弃所有修改    | `git reset --hard <commit-hash>` |
| 撤销已推送的提交 | 创建反向提交    | `git revert HEAD`                |
| 查看版本历史   | 查看提交日志    | `git log --oneline --graph`      |
| 查看某版本改动  | 查看具体变更    | `git show <commit-hash>`         |

**生产环境回退示例：**

```bash
# 1. 查看版本历史
git log --oneline --graph

# 2. 回退到上一个稳定版本
git revert HEAD --no-edit

# 3. 推送回退
git push origin main

# 4. 重新部署
docker-compose down
docker-compose up -d --build
```
