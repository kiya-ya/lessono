# 姐妹团数据统计报表

> 兔玩大数据平台姐妹团模块的数据统计与可视化报表系统，用于追踪 2026-07-17 新政策上线前后的关键指标变化。

---

## 功能特性

> 正式版为 **5 页结构**（概览 / 预警中心 / 厅分析 / 姐姐分析 / UID查询）+ 侧栏「姐姐筛选」子标签，对齐预览原型 `preview-visual.html`。

| 页面 | 功能 |
|------|------|
| 概览页 | 全局筛选栏（时间「月+周」双下拉在最前 + 类型/组/大厅三级联动，位于毕业妹妹留存与核心指标之间）+ 团分析（存活分析 / 解散原因分布 / 大厅对比 / 姐姐排行·当日）+ 核心指标 6 KPI（月视图率类=月内周均值、计数=整月合计，对比上一月）+ 平台级预警 3 卡 + 毕业妹妹留存跳转 + 明细数据（搜索/排序/分页/状态筛选/原因筛选含离职细分；保护期结束列=妹妹保护期；已成团天数=生命周期方框，点方框看该周明细/进完整团详情） |
| 预警中心 | 平台级预警 4 卡（姐妹团留存率 / 主动解散占比 / 新成团数 / 解散时间分布）+ 躺平预警（连续未陪档分布 + 大厅分布 + 躺平名单） |
| 厅分析 | 厅排行 + 各厅进行中团占比 + 礼物流水周趋势 + 单厅下钻 + 单厅解散原因构成（环形 + 近 8 周趋势） |
| 姐姐分析 | 姐姐画像 + 候选池（姐妹关系持续率 / 妹妹成长 / 培养升牌率 / 培养力总分四因子 + 加权综合分 + 倾斜动作结果记录）+ 毕业妹妹留存；侧栏「姐姐筛选」子标签直达候选池 |
| UID查询 | 本周 vs 上周对比、姐妹团参与信息、累计流水（server1 合计）、姐姐 vs 妹妹对比图（组合双轴：柱=流水 / 线=差额）、CSV导出 |

| 权限与适配 | 厅运营只看自己管理的厅、管理员看厅排行（按角色过滤）；手机端侧栏折叠为顶部横条，全页面响应式 |

## 首次使用

### 1. 配置登录（Cookie / 账号密码二选一）

Cookie 现在会**自动保活**（每 30 分钟心跳）并在失效时**自动重登**，正常情况无需手动维护：

- **自动重登**（推荐）：复制 `data/login_credentials.json.example` 为 `data/login_credentials.json`，填入账号密码（`userid` / `pwd`）。Cookie 失效时自动用 OCR 识别验证码重新登录两个系统（server1 / bigdata）。
- **手动兜底**：点击页面右上角 **🍪 Cookie 管理**，分别粘贴：
  - **UID 查询 Cookie**: 从 `server1.tuwan.com:10010` 页面复制
  - **数据抓取 Cookie**: 从 `bigdata.tuwan.com` 页面复制
  - Cookie 格式要求包含 `PHPSESSID`。

### 2. 抓取数据

首次使用数据库为空，需要手动抓取历史数据：

```bash
# 在项目目录执行
python daily_crawl.py
```

或配置 Windows 定时任务自动每日更新：
```bash
python setup_task.py
```

### 3. 使用 UID 查询

- 在 **👤 UID查询** 标签页输入 UID
- 勾选「模拟数据模式」可无需内网测试前端
- 关闭模拟模式需确保已更新有效 Cookie 且连接内网

## 核心指标计算说明

> **口径定稿（2026-08-17 grill 确认）**：指标以 **`team_detail` 明细快照重算**为准，`stats_daily` / `weekly_report` 不再作为指标真源（`stats_daily` 只有「全部」大厅、`reward_amount` 是奖励非流水、且 2026-08-01 起同日双行导致留存率减半）。`team_detail` 自 2026-07-27 起逐日积累。

### 奖励 vs 流水（两个独立指标，勿混）

| 名称 | 字段 | 含义 |
|------|------|------|
| **奖励** | `team_detail.reward_amount` | 官方发放的礼物奖励（快照日口径） |
| **流水** | `team_detail.sister_revenue` / `team_sister_revenue` | 自己挣的礼物流水（周口径） |

### 指标重算口径（周粒度，周一 → 周日）

```
新成团     = DISTINCT team_id WHERE form_date     ∈ [week_start, week_end]
非毕业解散 = DISTINCT team_id WHERE dissolve_date ∈ [week_start, week_end] AND dissolve_reason ≠ '毕业'
毕业数     = DISTINCT team_id WHERE dissolve_date ∈ [week_start, week_end] AND dissolve_reason = '毕业'
期初进行中 = 该周最早快照里 dissolve_date 为空的团数
期末进行中 = 该周最晚快照里 dissolve_date 为空的团数
留存率     = (期末进行中 − 新成团) ÷ 期初进行中     （老团留存）
解散率     = 非毕业解散 ÷ 期初进行中                （毕业不计入流失）
主动解散占比 = 主动解散 ÷ 非毕业解散
单团流水   = 周流水 ÷ 期末进行中                    （不叫「人均流水」）
在榜团数   = 期末进行中
平均在榜天 = AVG(days_since_formed) over 期末进行中的团
```

**术语说明：**
- **期初进行中**：本周最早快照里 `dissolve_date` 为空的团数
- **期末进行中**：本周最晚快照里 `dissolve_date` 为空的团数
- **本周新成团**：本周内新成立的姐妹团数量（按 `form_date`）
- **非毕业解散**：本周内解散且原因 ≠ 「毕业」的团数（满 30 天毕业不算流失）
- **毕业**：姐妹团满 30 天自动毕业（`dissolve_reason='毕业'`），与牌子/等级无关

### 页面指标归属

| 页面指标 | 归属 |
|---------|------|
| 姐姐排行榜「按当日奖励」 | 奖励（`reward_amount`） |
| 概览「单团流水」 | 流水（`sister_revenue`） |
| 对比页「礼物流水」 | 流水 |
| 明细表「奖励」列 | 奖励 |
| 画像「本周流水」 | 流水 |

### 数据层已知问题（历史背景）

- `team_detail` 是**当日快照**性质（`/sisters/detail/` 只返回当前团），首次抓取 2026-07-27，之前无团级明细 → 07-27 前只有 `stats_daily`（仅「全部」、奖励≠流水、日期推断丢星期几）
- `stats_daily` 2026-08-01 起每天出现两行（`cycle` 星期标签不一致），`infer_full_date` 丢星期几导致同日双行、留存率呈现「周末=周初一半」——已被 team_detail 重算取代

## 名词解释（术语表）

> 看板里出现的高频名词与其数据口径。核心公式见上文「核心指标计算说明」；领域术语的严格定义（含「避免混用」提示）另见根目录 `CONTEXT.md`。

### 角色与等级

| 名词 | 含义 |
|------|------|
| **姐姐** | 姐妹团中带人的一方（队长），负责带妹妹成长；实力强的姐姐值得被输送更多妹妹或提拔为管理 |
| **妹妹** | 与姐姐配对的新人，入场等级较低，在团期内成长；升到王牌/大神即到毕业线、可晋升为姐姐 |
| **姐妹团** | 姐姐与妹妹的一对一配对，周期约 30 天、到期自动毕业（解锁） |
| **牌子等级** | 团等级，从低到高：`无 → 初级铜牌 → 铜牌 → 初级银牌 → 银牌 → 金牌 → 王牌 → 大神`。排序/展示/门槛用线性秩；「妹妹成长」的 Δscore 用指数分值（大神 64 / 王牌 32 / 金牌 16 / 银牌 8 / 初级银牌 4 / 铜牌 2 / 初级铜牌 1 / 无 0，升一级难度约翻倍） |

### 快照与团生命周期

**快照日（`snapshot_date`）是什么？** 每天把 bigdata「基础数据明细页」整版抓下来存一份，抓取日期就是快照日。

- **每天一张，一个团一条**：`team_detail` 不是「事件流水」（不会只在成团/解散时记一笔），而是每天抓一次明细页，把当天页面上列出的每个团各存一条。某团 08-12 成团、08-16 解散，会在 08-12 ~ 08-16 及解散后残留的几天里，每个快照日各留一条。
- **页面是「进行中 + 近期解散」的滑动窗口**（不是只有当前在榜）：bigdata 明细页**固定 1000 条、无分页**（`?page=2` 等参数均被忽略，第 1~1000 条按「最新在前」排，超出窗口的老团彻底查不到），既含进行中的团，也含近期解散、尚未掉出窗口的团（实测 08-25 快照 = 521 进行中 + 479 已解散；已解散团残留平均约 10 天、最长 42 天）。
- **断档能补事件、补不回逐日状态**：某天抓取失败（如 Cookie 过期），只要断档期间成团/解散的团还没滑出窗口，它们的**成团日 / 解散日**还能在恢复后的快照里读到；但「某天在榜团数、某团某天是第几天」这种**逐日状态**没拍下来，只能靠成团日/解散日自己重算；滑出 1000 条窗口的团则彻底丢失。
- **统计时按团去重**：同一团跨多个快照日有多行，算「当前进行中团数」等指标时按 `team_id` 取最新一行（`MAX(rowid) … GROUP BY team_id`）。

| 名词 | 含义 |
|------|------|
| **快照 / 快照日** | 见上：每天抓取一版「当天在榜团」的状态，抓取日期记作 `snapshot_date` |
| **成团** | 姐姐与妹妹配对成功、团建立（按 `form_date` 计） |
| **毕业** | 团满 30 天正常结束（`dissolve_reason='毕业'`），与牌子/等级无关；**不算流失、不计入解散率** |
| **解散** | 团未满 30 天就结束（`dissolve_reason≠'毕业'`），即真正的流失，又称「非毕业解散」 |
| **期初 / 期末进行中** | 某周内最早 / 最晚快照日上 `dissolve_date` 为空（仍在榜）的团数；若周一/周日缺快照，自动退到周内最近一次快照 |

### 解散原因分类

官方解散规则（触发条件）共 6 条，`dissolve_reason` 据此归一化为 8 类、再按「谁发起」归为两大口径：

| # | 解散规则（触发条件） | 归一化原因 | 归类 |
|---|---------------------|-----------|------|
| 1 | 自绑定日起 30 个自然日为成长期，到期妹妹自动毕业、姐妹团解散 | 毕业 | 毕业（不算解散/流失） |
| 2 | 姐妹任意一方通过姐妹团页面解绑 | 手动解散 | 主动解散 |
| 3 | 姐妹任意一方从大厅离职（如妹妹被系统淘汰） | 离职（含「不在同一个大厅」=换厅） | 主动解散 |
| 4 | 姐妹任意一方被生态违规处罚（假车 / 买卖流水 / 一人多号 / 内部挖人 / 涉黄） | 生态违规 | 系统解散 |
| 5 | 姐妹等级同时低于铜牌 | 等级低于铜牌 | 系统解散 |
| 6 | 连续 5 日未完成陪档日常任务（日常2） | 任务未完成自动解散 | 系统解散 |

> 补充规则：**重新绑定新姐妹团后，任务与成就按新团重新开始计算**（非解散规则）。此外数据里还存在少量「注销」（账户注销）归为主动解散。

```
非毕业解散（= 流失） = 主动解散 + 系统解散
主动解散（用户侧）   = 手动解散 · 离职(含换厅) · 注销
系统解散            = 任务未完成自动解散 · 生态违规 · 等级低于铜牌 · 其他
解散率              = 非毕业解散 ÷ 期初进行中       （毕业不计入）
主动解散占比        = 主动解散 ÷ 非毕业解散
```

### 常用指标

| 名词 | 含义 |
|------|------|
| **留存率** | (期末进行中 − 本周新成团) ÷ 期初进行中（老团留存） |
| **解散率** | 非毕业解散 ÷ 期初进行中 |
| **主动解散占比** | 主动解散 ÷ 非毕业解散 |
| **单团流水** | 周流水 ÷ 期末进行中（不叫「人均流水」） |
| **在榜团数** | 期末进行中 |
| **平均在榜天** | 期末进行中团 `days_since_formed` 的平均值 |
| **头牌依赖度** | 某厅 TOP1 姐姐的当日奖励占该厅全部姐姐当日奖励的比例（≥40% 红 / ≥30% 黄，<500 元小厅不告警） |
| **奖励 vs 流水** | 两个独立指标，勿混：奖励=`reward_amount`（快照当日官方发放），流水=`sister_revenue`（自己挣的，周口径），详见上文 |

### 培养力指标（姐姐分析·候选池）

> 识别「值得培养的好姐姐」的四因子，均按 `team_detail` 快照逐团重算，与上文「核心指标」同源；后端 `/api/talent-pool`（`api_talent_pool`，`backend/app.py:1128`）。四因子已全部落地正式代码；仅「代际传承」下钻仍为占位（见下）。

| 名词 | 公式 / 口径 |
|------|------------|
| **姐妹关系持续率** | **Σ(已结束团实际存续天数) ÷ (已结束团数 × 30) × 100%**。毕业团按 30 天 clamp（快照滞后会虚高 31/32）、解散团按 `dissolve_date − form_date` 实际天数、**进行中团不进分子分母**。数学上 = 毕业率 + Σ(解散团存续比例)/已结束团数，**天然 ≥ 毕业率**。是带团毕业率的「连续化」升级：毕业率只看「成没成」，持续率还看「撑了多久」，更能反映姐姐维持关系的能力（例：A 姐带 2 妹，1 毕业 + 1 第 14 天解散 → (30+14)/60 = 73%；B 姐 1 毕业 + 1 第 8 天解散 → (30+8)/60 = 63%，两者毕业率同为 50%） |
| **带团毕业率**（辅助） | 自然毕业团数 ÷ 已结束团数 × 100%（进行中团不进；分母=自然毕业团+非毕业解散团，0→空）。**降为辅助副行**，作持续率的「毕业完成度」参考，不单独作候选门槛 |
| **妹妹成长** | **难度加权成长分/月** =（末期难度分 − 初期难度分）÷ 团龄天数 × 30，只对有成长的团取平均。末期/初期 = 该团末次/首次快照的妹妹最高等级难度分（`MAX−MIN`）；难度分指数递增：铜牌2 → 银牌8 → 金牌16 → 王牌32 → 大神64 |
| **培养升牌率** | **妹妹有成长（`MAX−MIN>0`，至少升过一级）的团数 ÷ 历史带团总数 × 100%**。不要求团仍进行中（进行中团最多 2 个，若加「团存活」则分子封顶 2、值随带团数趋 0） |
| **培养力总分** | **加权综合分（满分 100）**：`0.4×姐妹关系持续率 + 0.35×妹妹成长(归一化) + 0.25×培养升牌率`；妹妹成长归一化 = min(成长分/月, 20) / 20 × 100（T=20 定稿，20 ≈ 满分锚点）。**仅作排序参考、不进候选硬门槛**，权重为初值、可后台调参（持续率权重最高——先能稳住关系）。三指标 `retention`/`sister_growth`/`joint_growth` 由 `/api/talent-pool` 返回，前端纯计算 |
| **候选判定** | 三条**硬**规则：`姐妹关系持续率≥65% 且 妹妹成长>0 且 牌子≥银牌`（后端 `level_rank≥4`，即银牌及以上，`sister_level`）。牌子只作最低门槛、不参与打分排序——银牌但妹妹成长快的姐姐，比王牌但妹妹不成长的更值得培养（「培养力」与「牌子」解耦）。**65% 为占位阈值、待按真实分布重测**（持续率天然 ≥ 毕业率，故原「毕业率≥50%」门槛必须上调） |

> **姐妹关系持续率的平台级底座 = 预警中心「解散时间分布」**：非毕业解散按「成团 → 解散」存续天数分 4 周直方图，反映关系在哪段时间最容易破裂（第 2 周成团 8~14 天是高峰）。持续率是「个体姐姐维持能力」、解散时间分布是「平台整体破裂规律」，两者同源（都来自 `dissolve_date − form_date` 存续时长）。

### 毕业妹妹沉淀（姐姐分析·毕业妹妹）

> 毕业后的「留存 + 持续优秀」追踪，补「带团毕业率」只看能否顺利毕业、不看毕业后价值的缺口。已落地正式代码（表接 `recent_graduates` 真数据；「留存率 / 毕业后 30 天留存 / 带妹代数 / 来源」仍按预览标注「待落地」，依赖「回访」数据、后端暂无此口径）。

| 名词 | 公式 / 口径 |
|------|------------|
| **毕业妹妹沉淀率** | 毕业后仍持续留存/产出的妹妹 ÷ 毕业妹妹总数 × 100%（回挂到候选池作培养力质量校验，非培养力四因子之一） |
| **数据来源（双口径）** | **回访为主**：新毕业妹妹在毕业后 30 / 90 / 180 天用 uid_crawler 回访一次，记录留存、是否开始带妹妹、带妹代数；**近似兜底**：回访数据尚未攒够的老毕业妹妹，暂用「毕业后是否再次成团/当姐姐」近似，标注口径切换点 |
| **毕业后轨迹字段** | 毕业后留存（30/90/180 天，用 ≥/< 符号表示留存天数）、是否开始带妹妹（晋升为姐姐并带自己的妹妹）、带妹代数（师承深度） |
| **代际传承** ⏳ | 妹妹毕业后当姐姐、她带的妹妹又毕业，逐代回溯形成的代际链条。在明细表点击「已开始带妹妹」下钻查看该妹妹的完整师承链（整链代数 / 直接带妹 / 再下一辈毕业）。是培养力可复制的最强证据（进阶、可选） |

## 好姐姐识别算法

> 「能否用算法精准识别一个好姐姐」的分析结论（2026-08 定稿，分析题、无代码落地）。

**结论：协同过滤（CF）在此场景基本不适用——识别好姐姐本质是「单对象打分排序」，不是「推荐」问题。** 建议「加权综合分 → 标杆相似度 → 有监督模型」三步演进。

**为什么不用协同过滤：**

| 障碍 | 说明 |
|------|------|
| 缺「用户-物品」评分矩阵 | CF 需要「姐姐 × 妹妹」显式评分；本系统是一对一配对（一个团 = 一个姐姐带一个妹妹），不是「一个姐姐给多个妹妹打分」 |
| 样本稀疏 | 约 887 姐姐 / 1800 团，交互极稀，相似度算出来无意义 |
| 问题本质不同 | 「识别好姐姐」是给单个姐姐打分排序，不是「给某妹妹推荐一个姐姐」 |

**推荐路径（成本从低到高）：**

1. **加权综合分（当前已做）**——把姐妹关系持续率 / 妹妹成长 / 培养升牌率归一化后加权求和得「培养力总分」，可排序、可调权重；替换「三条硬规则」的一刀切，排出「谁最值得培养」的名次。
2. **标杆相似度（CF 的正确用法）**——运营标一批「已确认的好姐姐」作标杆，算每个姐姐与标杆的**特征向量相似度**（余弦/欧氏，kNN），按相似度排序找「最像标杆」的人。这是协同过滤在本场景唯一合理的位置（user-based 找相似）。
3. **有监督模型（等有标签再说）**——积累「被提拔 / 输送成功」正负标签后，上逻辑回归 / GBDT 二分类，直接输出「好姐姐概率」。

> 现状：约 887 样本、十几个特征，规则筛选 + 加权综合分已够用，CF 属杀鸡用牛刀且数据撑不起来。落地不动爬虫，纯后端 `/api/talent-pool` 加一列总分 + 前端排序列即可。

## 常见问题

**Q: 如何启动服务？**
A: 两种方式：
- 开发启动：`.venv311\Scripts\python.exe start.py`（自动打开浏览器）
- 生产部署：双击 `deploy.bat`

**Q: 如何按大厅筛选数据？**
A: 两种方式：
1. **顶部工具栏**的「全部大厅」下拉框 → 控制**整个页面**的数据范围（KPI、趋势图、明细表等）
2. **明细搜索框**输入大厅名称 → 只过滤**明细表格**的数据

**Q: 页面里搜索框很多，到底听谁的？**
A: 搜索框分两层、作用域不同，不打架：

| 层 | 位置 | 作用 |
|---|---|---|
| **页面级** | 每页顶部整条搜索栏 | 决定本页「看哪几个厅 / 哪段时间」，改它整页图表一起刷新。概览页=类型/组/大厅/时间；预警中心=大厅+时间 |
| **表格级** | 某张表上方的小输入框 | 只过滤紧挨着的那一张表，在已圈定范围里按团ID/姐姐/妹妹/大厅名定位某一行 |

规则：**先页面级圈范围 → 再表格级找行**。UID查询的输入框是「查一个人」的入口，独立于这两层；预警中心的「时间」周选择器与概览页同口径（本周/上周/自定义周）。

**Q: 如何清理临时调试文件？**
A: 双击运行项目根目录的 `clean_tests.bat`，自动清理 `tests/` 目录下的所有临时文件。

**Q: 页面空白怎么办？**
A: 按 `Ctrl+F5` 强制刷新清除缓存；检查后端是否启动；F12 控制台查看 JS 错误。

**Q: UID查询显示"Cookie过期"？**
A: 打开 UID查询页面 → F12 → Network → 复制 Cookie → 粘贴到 Cookie管理 → 保存。

**Q: 数据不更新？**
A: 检查 `data/last_update.json` 确认上次更新时间；运行 `python daily_crawl.py` 手动抓取；或配置定时任务 `python setup_task.py`。

**Q: 启动报 `ModuleNotFoundError`？**
A: 确保使用 `.venv311\Scripts\python.exe` 运行，而不是系统 Python。虚拟环境已包含所有依赖。
